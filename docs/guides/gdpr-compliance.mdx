# GDPR Compliance for Stellar dApps

The EU General Data Protection Regulation (GDPR) applies to any organisation that processes personal data of people in the European Economic Area — regardless of where the organisation is based. If your Stellar dApp has users in the EU, GDPR applies to you.

This tutorial covers who GDPR applies to, which data subject rights you must support, what records you must keep, and a pre-launch compliance checklist you can work through with your team.

> **Legal disclaimer:** This tutorial is provided for informational purposes only and does not constitute legal advice. Consult a qualified data protection attorney before making compliance decisions.

## Does GDPR Apply to Your dApp?

You are subject to GDPR if either of the following is true:

1. **Your organisation is established in the EU or EEA**, regardless of where your users are.
2. **You offer goods or services to people in the EU**, or you monitor the behaviour of people in the EU (e.g., analytics), regardless of where your organisation is based.

Most public-facing dApps meet condition 2 unless they explicitly geo-block EU users.

### The Stellar ledger tension

GDPR gives EU residents the right to have their personal data erased. On-chain data — including a user's Stellar public key, transaction history, and smart contract interactions — is immutable and cannot be deleted by anyone. You must disclose this limitation clearly **before** a user connects their wallet or submits a transaction. The standard approach is:

> "Transactions submitted through this application are recorded permanently on the Stellar public ledger. We cannot erase or modify on-chain data in response to deletion requests. All other personal data we hold (email, IP logs, etc.) can be deleted on request."

Treat the Stellar public key as **pseudonymous** personal data under GDPR if it can be linked to a natural person in your systems (e.g., because the user provided an email address). Apply appropriate protections.

## Data Subject Rights

GDPR grants individuals eight rights. The most relevant for a Stellar dApp are:

### Right of access (Article 15)

A user can ask what personal data you hold about them and receive a copy within 30 days. Implement a data-export endpoint in your backend:

```ts
// app/api/user/export/route.ts
import { NextResponse } from 'next/server';
import { getServerSession } from 'next-auth';
import { db } from '@/lib/db';

export async function GET() {
  const session = await getServerSession();
  if (!session?.user?.id) return NextResponse.json({ error: 'Unauthenticated' }, { status: 401 });

  const user = await db.user.findUnique({
    where: { id: session.user.id },
    select: {
      email: true,
      createdAt: true,
      stellarPublicKey: true,
      // Include all fields you hold
    },
  });

  return NextResponse.json({ data: user });
}
```

### Right to erasure (Article 17)

A user can request deletion of their personal data. You must comply unless a legal obligation requires you to retain it. On-chain data is out of scope (it cannot be erased). Off-chain identifiable data — email, name, IP logs — must be deleted or anonymised.

```ts
// app/api/user/delete/route.ts
export async function DELETE() {
  const session = await getServerSession();
  if (!session?.user?.id) return NextResponse.json({ error: 'Unauthenticated' }, { status: 401 });

  await db.user.update({
    where: { id: session.user.id },
    data: {
      email: null,
      name: 'Deleted User',
      deletedAt: new Date(),
    },
  });

  // Revoke all sessions
  await db.session.deleteMany({ where: { userId: session.user.id } });

  return NextResponse.json({ message: 'Account deleted. On-chain data cannot be removed.' });
}
```

### Right to rectification (Article 16)

A user can ask you to correct inaccurate personal data. For a Stellar dApp this typically means correcting a stored email address or display name. Provide a standard profile-editing flow.

### Right to data portability (Article 20)

A user can request their data in a machine-readable format (JSON or CSV) so they can transfer it to another service. Your data-export endpoint (see Article 15 above) satisfies this right if it returns JSON.

### Right to object to processing (Article 21)

A user can object to processing based on legitimate interests, including direct marketing. If you send marketing emails, include an unsubscribe link in every message and honour opt-out requests immediately.

## Record Keeping — Article 30

Article 30 requires organisations to maintain a **Record of Processing Activities (RoPA)**. For organisations with fewer than 250 employees, the obligation applies only where processing is "not occasional" (which regular dApp use is) or involves special categories of data.

### What your RoPA must include

- Name and contact details of the controller (your organisation) and, if applicable, the Data Protection Officer
- The purposes of the processing
- A description of the categories of data subjects and personal data
- Categories of recipients
- Where applicable, transfers to third countries and the safeguards in place
- Intended erasure time limits
- A description of the technical and organisational security measures

### Minimal RoPA template

```markdown
# Record of Processing Activities — [dApp Name]

**Controller:** [Legal entity name], [Address]
**Contact:** [privacy@example.com]
**Last updated:** [YYYY-MM-DD]

---

## Processing activity 1 — User account management

| Field | Value |
|-------|-------|
| Purpose | Create and manage user accounts |
| Legal basis | Contract (Article 6(1)(b)) |
| Data subjects | Registered users |
| Personal data categories | Email address, Stellar public key, creation timestamp |
| Recipients | Internal engineering team; email delivery provider ([Provider name]) |
| Third-country transfers | [Provider name] — covered by Standard Contractual Clauses |
| Retention | Until account deletion; email logs 90 days |
| Security measures | Encryption at rest (AES-256), TLS in transit, access control |

---

## Processing activity 2 — Server logs

| Field | Value |
|-------|-------|
| Purpose | Security, abuse prevention, debugging |
| Legal basis | Legitimate interests (Article 6(1)(f)) |
| Data subjects | All visitors |
| Personal data categories | IP address, user-agent string, request path, timestamp |
| Recipients | Internal engineering team |
| Third-country transfers | None (self-hosted) or [Cloud provider — SCCs] |
| Retention | 30 days (automated log rotation) |
| Security measures | Access restricted to engineering team; logs not backed up beyond 30 days |

---

## Processing activity 3 — Analytics

| Field | Value |
|-------|-------|
| Purpose | Understanding usage patterns, product improvement |
| Legal basis | Legitimate interests / consent (depending on tool and configuration) |
| Data subjects | All visitors |
| Personal data categories | Anonymised page views, event counts (no PII after anonymisation) |
| Recipients | [Analytics provider name] |
| Third-country transfers | [Provider name — SCCs or adequacy decision] |
| Retention | Anonymised after 12 months; raw (pre-anonymisation) data 30 days |
| Security measures | Anonymisation before storage; pseudonymisation in transit |
```

## Pre-Launch Compliance Checklist

Work through this list before making your dApp publicly available to EU users.

### Legal basis

- [ ] Identified the legal basis for every processing activity in your RoPA (contract, legitimate interests, consent, etc.)
- [ ] Where consent is the basis (e.g., marketing emails), built a consent-capture UI and stored consent records

### Transparency

- [ ] Published a privacy policy that covers all processing activities
- [ ] Privacy policy is linked from the sign-up flow and the app footer
- [ ] Disclosed the permanent nature of on-chain data before users connect a wallet
- [ ] Disclosed all third-party processors (Horizon, analytics, email provider, etc.)

### Data subject rights

- [ ] Account deletion flow removes all identifiable off-chain data
- [ ] Data export endpoint returns all data held about the user in JSON
- [ ] Unsubscribe link present in all marketing emails
- [ ] Support email (or form) published for rights requests; response within 30 days

### Record keeping

- [ ] Article 30 RoPA created and stored internally
- [ ] RoPA reviewed with legal counsel (or a qualified DPO if required)

### Security

- [ ] Personal data encrypted at rest
- [ ] TLS enforced for all connections
- [ ] Access to personal data limited to personnel who need it
- [ ] Incident response plan documented (72-hour breach notification to the relevant supervisory authority)

### Third-party processors

- [ ] Data Processing Agreements (DPAs) signed with all third-party processors that handle EU personal data
- [ ] Third-country transfers covered by Standard Contractual Clauses or an adequacy decision

### Cookies and tracking

- [ ] Cookie consent banner implemented if you use tracking cookies (analytics, marketing)
- [ ] Cookie policy published and linked from the banner
