# Production Deployment Guide (Vercel + Nextellar Cloud)

This guide covers deploying a Nextellar dApp to production using **Vercel** for frontend hosting and **Nextellar Cloud** for backend infrastructure. You'll learn environment management, continuous deployment, performance tuning, and incident response.

## Part 1: Vercel Frontend Deployment

### Prerequisites

- A Nextellar Next.js project in a GitHub repository
- Vercel account linked to your GitHub
- All environment variables documented in `.env.example`

### Step 1.1: Connect Repository to Vercel

1. Visit [vercel.com/new](https://vercel.com/new)
2. Import your GitHub repository
3. Vercel auto-detects Next.js configuration
4. Click **Deploy**

### Step 1.2: Configure Environment Variables

In the Vercel dashboard:

1. Go to **Settings** → **Environment Variables**
2. Add production variables:

```
NEXT_PUBLIC_STELLAR_NETWORK=public
NEXT_PUBLIC_RPC_URL=https://horizon.stellar.org
NEXT_PUBLIC_SOROBAN_RPC=https://soroban-mainnet.stellar.org:443
NEXT_PUBLIC_WALLET_NETWORK=MAINNET
```

3. For API keys and secrets (if using Nextellar Cloud):

```
NEXTELLAR_API_KEY=sk_prod_xxxxxxxxxxxxx
NEXTELLAR_API_SECRET=ss_prod_xxxxxxxxxxxxx
```

> **Security Note**: Never commit `.env.local` or secrets to Git. Use Vercel's Environment Variables panel exclusively.

### Step 1.3: Custom Domain & SSL

1. Go to **Settings** → **Domains**
2. Add your production domain (e.g., `app.example.com`)
3. Vercel automatically provisions SSL certificates via Let's Encrypt
4. Point your domain's DNS records to Vercel's nameservers

### Step 1.4: Deployment Preview

Every pull request automatically generates a preview deployment. Preview URLs follow the pattern:

```
https://pr-123-your-repo.vercel.app
```

These preview environments use the same build process and environment variables (scoped to `preview` environment) as production, allowing QA and stakeholders to review changes before merge.

## Part 2: Nextellar Cloud Backend Configuration

### Prerequisites

- Nextellar Cloud account ([cloud.nextellar.dev](https://cloud.nextellar.dev))
- Production organization created
- API credentials generated

### Step 2.1: Create Production Project

1. Log in to Nextellar Cloud
2. Click **New Project**
3. Name: `dapp-prod` (or your project name)
4. Region: Select the region closest to your primary user base
5. Click **Create**

### Step 2.2: Configure API Gateway

Set up rate limiting and request routing:

```bash
## Example: Nextellar Cloud CLI
nextellar cloud config --project dapp-prod

## Set rate limits
nextellar cloud ratelimit --rpm 1000 --burst 100

## Configure CORS
nextellar cloud cors --allow-origins "https://app.example.com"
```

## Step 2.3: Database & State Management

If your dApp requires persistent state (leaderboards, user data, analytics):

1. Provision a PostgreSQL instance in Nextellar Cloud
2. Store connection string in Vercel environment variables as `DATABASE_URL`
3. Run migrations on every deployment:

```bash
## In Vercel deployment settings, add to "Build Command":
npm run build && npm run migrate:prod
```

Example migration script (`scripts/migrate-prod.js`):

```javascript
import { pool } from '@/lib/db.js';

const migrations = [
  `CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    public_key VARCHAR(56) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
  )`,
  `CREATE TABLE IF NOT EXISTS transactions (
    id SERIAL PRIMARY KEY,
    user_id INT NOT NULL,
    tx_hash VARCHAR(64) UNIQUE NOT NULL,
    status VARCHAR(20) DEFAULT 'pending',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(id)
  )`,
];

async function migrate() {
  for (const sql of migrations) {
    await pool.query(sql);
    console.log('✓ Migration executed');
  }
  await pool.end();
}

migrate().catch((err) => {
  console.error('Migration failed:', err);
  process.exit(1);
});
```

## Part 3: Environment Management

### Separate Configurations by Environment

Create `.env` files for each stage:

**`.env.development`** (local testing):

```
NEXT_PUBLIC_STELLAR_NETWORK=testnet
NEXT_PUBLIC_RPC_URL=https://horizon-testnet.stellar.org
```

**`.env.staging`** (Vercel preview):

```
NEXT_PUBLIC_STELLAR_NETWORK=testnet
NEXT_PUBLIC_RPC_URL=https://horizon-testnet.stellar.org
```

**`.env.production`** (Vercel production):

```
NEXT_PUBLIC_STELLAR_NETWORK=public
NEXT_PUBLIC_RPC_URL=https://horizon.stellar.org
```

In Vercel dashboard, assign each to the appropriate deployment environment.

### Validating Environment at Build Time

Add validation to `next.config.js`:

```javascript
export default {
  env: {
    NEXT_PUBLIC_RPC_URL: process.env.NEXT_PUBLIC_RPC_URL,
  },
  webpack: (config, { isServer }) => {
    if (!process.env.NEXT_PUBLIC_RPC_URL) {
      throw new Error('Missing NEXT_PUBLIC_RPC_URL in environment');
    }
    return config;
  },
};
```

## Part 4: CI/CD and Deployment Checks

### Automated Checks Before Production

Vercel can be configured to require all checks to pass before allowing production deployment:

```yaml
## .github/workflows/pre-deploy-checks.yml
name: Pre-Deployment Checks
on:
  pull_request:
    branches: [main]

jobs:
  checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '18'
          cache: 'npm'

      - run: npm ci
      - run: npm run lint
      - run: npm run type-check
      - run: npm run build
      - run: npm run test:unit

      # Verify Stellar network connectivity
      - name: Test RPC Connectivity
        run: |
          curl -s https://horizon.stellar.org/health || exit 1
          curl -s https://soroban-mainnet.stellar.org/health || exit 1
```

In Vercel settings, require this workflow to pass before allowing production deploys.

## Part 5: Scaling & Performance

### Vercel Scaling Strategies

1. **Automatic Scaling**: Vercel scales serverless functions automatically. No configuration needed for traffic spikes up to the plan limit.

2. **Edge Middleware**: Use Vercel Edge Functions for low-latency geolocation redirects and feature flags:

```typescript
// middleware.ts
import { NextRequest, NextResponse } from 'next/server';

export function middleware(request: NextRequest) {
  const country = request.geo?.country || 'US';

  // Route based on geography
  if (country === 'CN') {
    return NextResponse.redirect('/compliance/restricted');
  }

  return NextResponse.next();
}

export const config = {
  matcher: ['/app/:path*'],
};
```

3. **ISR (Incremental Static Regeneration)**: Cache static pages and revalidate on-demand:

```typescript
// pages/leaderboard.tsx
export async function getStaticProps() {
  const leaderboard = await fetchLeaderboard();

  return {
    props: { leaderboard },
    revalidate: 3600, // Revalidate every hour
  };
}
```

### Nextellar Cloud Scaling

Use Nextellar Cloud's auto-scaling workers:

```bash
nextellar cloud workers --scale-min 2 --scale-max 10 --cpu-target 70
```

## Part 6: Monitoring & Observability

### Vercel Analytics

1. **Performance Metrics**: Dashboard automatically tracks Core Web Vitals (LCP, FID, CLS)
2. **Function Execution**: Monitor serverless function duration and cold start times
3. **Usage Dashboard**: Track bandwidth, concurrent connections, and deployment frequency

Access via Vercel dashboard → **Analytics**.

### Application Monitoring with Nextellar Cloud

Monitor dApp-specific metrics:

```typescript
// lib/monitoring.ts
import { nextellarCloud } from '@nextellar/cloud';

export const monitor = nextellarCloud.monitoring();

// Track custom events
monitor.recordEvent('contract_invoked', {
  contractId: 'C...',
  method: 'transfer',
  duration: 250, // ms
  status: 'success',
});

// Track errors
monitor.recordError('soroban_simulation_failed', {
  contractId: 'C...',
  errorCode: 'ERR_RESOURCE_LIMIT_EXCEEDED',
});
```

### Logging & Error Tracking

1. **Vercel Logs**: All `console.log` and `console.error` statements appear in Vercel's real-time logs
2. **Third-party Integration**: Connect Sentry for error tracking:

```bash
## Install Sentry
npm install @sentry/nextjs

## Set SENTRY_AUTH_TOKEN in Vercel environment
```

## Part 7: Database & State Management in Production

### Connection Pooling

In Nextellar Cloud, connection pooling is automatically managed. For external databases:

```typescript
// lib/db.ts
import pg from 'pg';

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20, // Connection pool size
  idleTimeoutMillis: 30000,
  connectionTimeoutMillis: 2000,
});

pool.on('error', (err) => {
  console.error('Unexpected error on idle client', err);
});

export default pool;
```

### Backup Strategy

1. **Automated Backups**: Nextellar Cloud performs daily backups
2. **Retention**: 30-day backup retention by default
3. **Point-in-Time Recovery**: Request backup restore via support dashboard

## Part 8: Rollback Procedures

### Vercel Quick Rollback

If a deployment introduces issues:

1. Go to Vercel dashboard → **Deployments**
2. Find the last stable deployment
3. Click **⋯** → **Promote to Production**

This redeploys the previous stable code immediately (~30 seconds).

### Database Rollback

For critical database issues:

1. Contact Nextellar Cloud support with the restore timestamp
2. Team initiates point-in-time recovery
3. Application restored to known-good state

### Manual Rollback Checklist

- [ ] Identified root cause of production issue
- [ ] Verified rollback candidate deployment is stable
- [ ] Notified relevant stakeholders (support, ops)
- [ ] Executed rollback on Vercel
- [ ] Monitored error rates for 5 minutes post-rollback
- [ ] Documented incident and prevention measures

## Part 9: Security Checklist

- [ ] SSL/TLS certificate enabled and auto-renewed
- [ ] Environment variables use Vercel's secure storage (not hardcoded)
- [ ] API keys and secrets stored only in Vercel environment variables
- [ ] CORS configured to allow only your domain
- [ ] Rate limiting enabled on API Gateway
- [ ] Database credentials never logged
- [ ] Wallet private keys never exposed in logs or error messages
- [ ] DDoS protection enabled (Vercel default)
- [ ] Staging environment uses testnet Stellar endpoints
- [ ] Production environment uses mainnet endpoints

## Part 10: Troubleshooting

### Build Failures

Common issues and solutions:

| Issue                        | Cause                     | Solution                                                  |
| ---------------------------- | ------------------------- | --------------------------------------------------------- |
| Missing environment variable | `.env.example` not synced | Add variable in Vercel → Settings → Environment Variables |
| Node version mismatch        | Local Node ≠ Vercel Node  | Specify `engines.node` in `package.json`                  |
| pnpm lock mismatch           | Lockfile out of sync      | Run `pnpm install` locally and commit `pnpm-lock.yaml`    |

### Runtime Errors

| Issue                       | Cause                               | Solution                                              |
| --------------------------- | ----------------------------------- | ----------------------------------------------------- |
| RPC connection timeout      | Network latency or endpoint down    | Check endpoint status, increase timeout in SDK config |
| Soroban simulation fails    | Resource limit exceeded             | Optimize contract storage/computation                 |
| Database connection refused | Pool exhausted or credentials wrong | Check `DATABASE_URL`, verify pool size limits         |

### Performance Issues

| Issue                      | Cause                              | Solution                                        |
| -------------------------- | ---------------------------------- | ----------------------------------------------- |
| High Core Web Vitals (LCP) | Large bundle or unoptimized images | Enable Next.js Image Optimization, code split   |
| Cold starts > 5s           | Infrequent function invocations    | Keep function warm with periodic health checks  |
| Database slow queries      | Missing indexes or N+1 queries     | Add indexes, batch queries in application layer |
