# Contributing to Documentation

This guide explains how to contribute to Nextellar documentation, with a focus on understanding the content build pipeline and development workflow.

## Content Build Process

Nextellar documentation uses **Contentlayer** to process MDX files into structured, type-safe content objects. Understanding this build step is essential for contributors.

### What the Content Build Does

The content build process (`pnpm build:content`) performs several important tasks:

**Content Processing**

- Converts MDX files into structured JavaScript objects.
- Validates frontmatter schema and required fields.
- Processes embedded React components and imports.
- Generates type definitions for content objects.

**Navigation & Search**

- Creates navigation tree from file structure and frontmatter.
- Builds search index for documentation content.
- Generates sitemap and internal link mappings.
- Validates cross-references between documents.

**Optimization**

- Optimizes images and static assets referenced in content.
- Bundles and tree-shakes unused code from MDX components.
- Creates efficient data structures for fast page loading.
- Generates static props for Next.js pages.

### Running the Content Build

**Basic Command**

```bash
pnpm build:content
```

**What happens during the build:**

```bash
✓ Generated 47 documents in .contentlayer
✓ Validated frontmatter for all MDX files
✓ Built navigation tree (4 sections, 23 pages)
✓ Generated search index (1,247 searchable items)
✓ Validated 156 internal links
```

**Integration with Development**

```bash
# Full development build
pnpm build          # Runs build:content + next build

# Development server (auto-rebuilds content)
pnpm dev           # Watches for MDX changes
```

### When You Must Run the Content Build

**Required Scenarios**

- **Adding new MDX files**: New pages need to be processed and indexed
- **Modifying frontmatter**: Changes to title, description, or metadata
- **Updating internal links**: Cross-references need validation
- **Before production build**: Always runs as part of `pnpm build`

**Automatic Rebuilds**

- **Development mode**: Content rebuilds automatically when MDX files change
- **CI/CD pipeline**: Runs during automated builds and deployments
- **Pre-commit hooks**: Validates content before commits (optional)

**Manual Rebuilds Needed**

- **After git pull**: When pulling changes that include new content
- **Troubleshooting**: When content seems out of sync
- **Before testing**: To ensure latest content is available

### Content Build Configuration

The build process is configured in `contentlayer.config.ts`:

```typescript
import { defineDocumentType, makeSource } from 'contentlayer2/source-files';

const Doc = defineDocumentType(() => ({
  name: 'Doc',
  filePathPattern: `**/*.mdx`,
  contentType: 'mdx',
  fields: {
    title: { type: 'string', required: true },
    description: { type: 'string', required: true },
    // Additional fields...
  },
  computedFields: {
    url: {
      type: 'string',
      resolve: (doc) => `/${doc._raw.flattenedPath}`,
    },
    // Navigation and search fields...
  },
}));

export default makeSource({
  contentDirPath: 'docs',
  documentTypes: [Doc],
  mdx: {
    remarkPlugins: [remarkGfm],
    rehypePlugins: [rehypeSlug, rehypeHighlight],
  },
});
```

### Troubleshooting Content Build Issues

**Common Error: Invalid Frontmatter**

```bash
Error: Missing required field "description" in docs/guides/example.mdx
```

**Solution**: Ensure all MDX files have required frontmatter:

```yaml
---
title: 'Page Title'
description: 'Page description for SEO and navigation'
---
```

**Common Error: Broken Internal Links**

```bash
Error: Link target not found: /docs/nonexistent-page
```

**Solution**: Verify link targets exist and use correct paths:

```markdown
<!-- Correct -->

[CLI Commands](/docs/cli/commands)

<!-- Incorrect -->

[CLI Commands](/docs/cli/nonexistent)
```

**Common Error: MDX Syntax Issues**

```bash
Error: Unexpected token in docs/guides/example.mdx:15:3
```

**Solution**: Check MDX syntax, especially JSX components:

```markdown
{/_ Correct _/}

<div className="grid grid-cols-2">Content here</div>

{/_ Incorrect - missing closing tag _/}

<div className="grid grid-cols-2">
  Content here
```

**Frontmatter Validation**

```typescript
// Required fields for all documents
interface DocumentFrontmatter {

  description: string; // SEO description
}
```

**Link Validation**

```bash
# Check all internal links
pnpm check:links

# Output example
✓ Validated 156 internal links

  - /docs/cli/nonexistent (referenced in docs/cli/commands.mdx:45)
```

**Content Structure Validation**

- Ensures proper heading hierarchy (h1 → h2 → h3).
- Validates code block language specifications.
- Checks for required sections in specific document types.

## Development Workflow

### Setting Up for Development

1. **Clone and Install**

```bash
git clone https://github.com/nextellarlabs/nextellar-docs.git
cd nextellar-docs
pnpm install
```

2. **Initial Content Build**

```bash
pnpm build:content
```

3. **Start Development Server**

```bash
pnpm dev
```

### Making Content Changes

**For New Pages**

1. Create MDX file in appropriate `docs/` subdirectory
2. Add required frontmatter
3. Run `pnpm build:content` to process new file
4. Verify page appears in navigation

**For Existing Pages**

1. Edit MDX file (auto-rebuilds in dev mode)
2. Check browser for immediate updates
3. Validate changes with `pnpm check:links`

**For Navigation Changes**

1. Update file structure or frontmatter
2. Run `pnpm build:content` to regenerate navigation
3. Test navigation in browser

## Validation Scripts

Before submitting a pull request, run the validation scripts to catch common issues. These scripts are designed to run against source files without requiring a dev server.

### check:links

**Purpose**: Validates all internal links in documentation files. Checks that every link target (`/docs/...`) points to an actual documentation file and that anchor links (`#section-name`) exist on their target pages.

**Command**

```bash
pnpm check:links
```

**What It Validates**

- All internal links (starting with `/`) point to existing documentation files
- Anchor links (`#section-name`) match actual headings on target pages
- Both Markdown link syntax (`[text](url)`) and HTML href attributes
- Supports links with or without the `/docs` prefix

**Success Output**

```
🔗 STATIC LINK CRAWLER

Scanning docs directory: <path>/docs

Found 247 documentation files

Validation Results:
✅ Valid links: 1,247/1,247

🎉 ALL LINKS VALID!
```

**Failure Output Example**

```
❌ Broken links: 3

Broken Links Report:

/docs/cli/commands
  [1] Line 45
       Link: /docs/components/nonexistent
       Error: page not found
       Text: "Example Component"

/docs/guides/contributing
  [2] Line 128
       Link: /docs/missing-section
       Error: page not found

/docs/getting-started/faq
  [3] Line 87
       Link: #invalid-anchor
       Error: anchor '#invalid-anchor' not found on this page

❌ VALIDATION FAILED - 3 broken link(s) found
```

**How to Fix Broken Links**

1. **Page not found**: Verify the target file exists in `docs/`. Use correct path format: `/docs/section/filename` (without `.mdx` extension)
2. **Anchor not found**: Ensure the heading exists on the target page. Anchors are auto-generated from markdown headings (spaces → hyphens, lowercase)
3. **Missing `/docs` prefix**: Links can use `/docs/...` or shortened forms, but must start with `/`

**Prerequisites**

- No dev server needed — runs against source files only
- Can be run anytime during development

### validate:sidebar

**Purpose**: Validates that all component links in sidebar configuration (`config/sidebar.tsx`) and table of contents (`config/toc.tsx`) match actual component files in `docs/components/`. Ensures navigation references don't break when components are added, renamed, or deleted.

**Command**

```bash
pnpm validate:sidebar
```

**What It Validates**

- All component links in `config/sidebar.tsx` point to existing `.mdx` files in `docs/components/`
- All component links in `config/toc.tsx` point to existing `.mdx` files in `docs/components/`
- Detects components that exist but aren't listed in navigation
- Generates a JSON report for CI/automation

**Success Output**

```

✅ VALID SIDEBAR LINKS (2):
  - connect-wallet-button
  - use-window-size

📋 TOC CLAIMS
CLAIMS (1): connect-wallet-button

✅ VALID TOC ENTRIES (1):
  - connect-wallet-button

✅ SUMMARY

TOC: 1/1 valid (100%)
Total broken: 0

🎉 ALL COMPONENT REFERENCES ARE VALID!

💾 sidebar-validation.json updated
```

**Failure Output Example**

```
🔍 COMPONENTS INVENTORY (SOURCE OF TRUTH)

```

**How to Fix Broken References**

1. **Component doesn't exist**: Check spelling in `config/sidebar.tsx` and `config/toc.tsx`. Ensure the component file exists in `docs/components/` with matching name
2. **Recently added component**: If you added a new component but it's not showing in navigation, add its link to `config/sidebar.tsx` or `config/toc.tsx`
3. **Deleted a component**: Remove the corresponding link from both config files

**Prerequisites**

- No dev server needed — runs against config files and component directory only
- Can be run anytime during development
- Generates `sidebar-validation.json` in project root (tracked in git)

**When to Use**

- **Before opening a PR**: Run both scripts to catch issues early
- **After renaming components**: Always validate sidebar references match new names
- **When adding new components**: Add to config files, then run to verify

### Pre-Submission Checklist

Before submitting a pull request:

```bash
# 1. Build content successfully
pnpm build:content

# 2. Validate all links
pnpm check:links

# 3. Validate sidebar references
pnpm validate:sidebar

# 4. Check formatting
pnpm format:check

# 5. Run linting
pnpm lint

# 6. Test full build
pnpm build
```

**All commands should complete without errors.**

For a quick ready-to-use checklist, see [Documentation Contributing Checklist](/docs/guides/contributing-checklist).

```text

├── getting-started/       # Installation, quick start

├── examples/             # Code examples
```

### Frontmatter Requirements

```yaml
---
title: 'Descriptive Page Title'
description: 'Clear description for SEO and navigation (50-160 chars)'
---
```

### Writing Style

- Use clear, concise language.
- Include code examples for technical concepts.
- Structure content with proper headings.
- Add internal links to related documentation.

## Getting Help

**Build Issues**

- Check the terminal output for specific error messages.
- Verify MDX syntax and frontmatter format.
- Ensure all internal links are valid.

**Content Questions**

- Review existing documentation for patterns.
- Check the [Docs Style Guide](/docs/guides/style-guide) for writing conventions.
- Ask in [GitHub Discussions](https://github.com/nextellarlabs/nextellar/discussions).

**Technical Problems**

- Clear `.contentlayer` directory and rebuild.
- Restart development server.
- Check Node.js version compatibility (requires Node 18+).

## Stellar Wave Program & Contributor Rewards Payouts

Nextellar participates in the **Stellar Wave Program** organized in collaboration with [Drips Network](https://www.drips.network/wave). The program provides decentralized, transparent rewards for open-source contributions.

### How Rewards Work

1. **Issue Application & Assignment**:
   Contributors apply to open Wave issues directly on GitHub using the Drips Wave bot (`drips-wave`). Maintainers review applications and assign issues with established difficulty tiers (e.g., Easy: 100 pts, Medium: 150 pts, Hard: 200 pts).
2. **Review & Points Accrual**:
   Upon submitting a linked pull request before the cycle due date and receiving maintainer approval, points are awarded to the contributor's account.
3. **Automated On-Chain Reward Distribution**:
   At the close of each Wave cycle, rewards from the allocated reward pool are distributed automatically on-chain via smart contracts directly to contributors' registered addresses.
4. **Verifying Payouts & Proof of Payment**:
   Contributors can track point accumulation, cycle settlements, and on-chain transaction hashes directly on the [Drips Wave Platform](https://www.drips.network/wave) and verify transaction execution on Stellar/EVM network block explorers.
