# Time Locked Transactions

Every Stellar transaction can carry a **time bounds** field — a `minTime` / `maxTime` pair, both Unix timestamps — that restricts the ledger close times during which the transaction is valid. Validators reject the transaction outside that window, before touching its operations. Time bounds are what makes pre-signed transactions safe to hand out ahead of time: a scheduled payment, an escrow release, or a signed-but-not-yet-submitted authorization all rely on the network — not the holder of the signed envelope — enforcing _when_ it can apply.

This guide covers where time-locked transactions are useful, how to construct and submit them, and the pitfalls that catch most implementations.

---

## Use cases

| Use case                             | How time bounds are used                                                                                                                                                         |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Scheduled disbursements              | Sign a payment now with `minTime` set to a future payout date; anyone can submit it once that time arrives, but not before                                                       |
| Escrow release windows               | Combine a pre-signed transaction with a `minTime`/`maxTime` window so a counterparty can only execute the release within an agreed period                                        |
| Expiring pre-authorized transactions | Distribute a signed transaction (e.g. a multisig payout) that becomes invalid after `maxTime`, so an old authorization can't be replayed indefinitely                            |
| Invoice payment windows              | Require a payment to land within a fixed window after issuance, after which the invoice transaction simply stops being submittable                                               |
| Atomic multi-party agreements        | Coordinate several pre-signed transactions (e.g. a swap) that all share a `maxTime`, so if not everyone submits in time, none of the individual legs can execute alone afterward |

Time bounds gate the **whole transaction** — every operation inside it. If you need to gate an individual balance's claimability instead (e.g. "recipient can claim after date X"), that's a job for claim predicates on a claimable balance, not transaction time bounds — see [Claimable Balances](/docs/guides/claimable-balances).

## Construction and submission

`TransactionBuilder` exposes time bounds two ways: explicitly via `.setTimebounds()`, or implicitly via `.setTimeout()`.

### Explicit time bounds

```typescript
import { TransactionBuilder, Networks, Operation } from '@stellar/stellar-sdk';

const minTime = Math.floor(Date.now() / 1000) + 60 * 60 * 24 * 7; // in 7 days
const maxTime = minTime + 60 * 60 * 24; // valid for a 24h window

const tx = new TransactionBuilder(sourceAccount, {
  fee: '100',
  networkPassphrase: Networks.PUBLIC,
})
  .addOperation(
    Operation.payment({
      destination: 'GBOB...',
      asset: Asset.native(),
      amount: '500',
    })
  )
  .setTimebounds(minTime, maxTime)
  .build();

tx.sign(sourceKeypair);
// Hand `tx.toXDR()` to whoever should submit it once minTime arrives
```

A `minTime` of `0` means "valid immediately" — that's the default when you don't set time bounds explicitly through `setTimeout`.

### Implicit time bounds via `setTimeout`

Most transactions don't need a scheduled _start_, just an expiry so a submission attempt doesn't hang around forever:

```typescript
const tx = new TransactionBuilder(sourceAccount, {
  fee: '100',
  networkPassphrase: Networks.PUBLIC,
})
  .addOperation(Operation.payment({ destination, asset, amount }))
  .setTimeout(180) // maxTime = now + 180s, minTime = 0
  .build();
```

`setTimeout(seconds)` sets `maxTime` to `seconds` from the moment it's called — not from when the transaction is later submitted or signed. `setTimebounds` must be called before `setTimeout`, or `setTimeout` will overwrite it; the SDK throws if you call `setTimeout` after `setTimebounds` with a nonzero `maxTime` already set, to stop you from silently clobbering an intentional window.

### Submission

Submission is unchanged from any other transaction — Horizon evaluates time bounds against the ledger the transaction would be included in:

```typescript
try {
  const result = await server.submitTransaction(tx);
} catch (err) {
  const resultCodes = err?.response?.data?.extras?.result_codes;
  if (resultCodes?.transaction === 'tx_too_early') {
    // current ledger close time < minTime
  }
  if (resultCodes?.transaction === 'tx_too_late') {
    // current ledger close time > maxTime
  }
}
```

## Pitfalls and edge cases

**Clock drift between your machine and ledger close time.** `minTime`/`maxTime` are compared against the _ledger's_ close time, not your local clock at signing time. If your system clock is skewed, a transaction you believe has 30 seconds left may already be expired on-chain. Don't cut windows close; build in slack (tens of seconds, not milliseconds) especially for anything computed relative to `Date.now()`.

**`setTimeout` measures from call time, not submission time.** A transaction built with `setTimeout(180)` and then held for five minutes before signing and submitting is already expired — `maxTime` was fixed the moment `setTimeout` ran. Call `setTimeout` (or `setTimebounds`) as close as possible to submission, not at transaction-construction time if there's meaningful delay between building and sending.

**Expired pre-signed transactions can't be "renewed."** Time bounds are part of what gets signed. If a transaction expires before it's submitted, you cannot bump `maxTime` and reuse the existing signatures — the transaction hash (and therefore the signatures over it) changes. You must rebuild with new time bounds and collect signatures again, which defeats the purpose of a pre-signed authorization if the signers aren't available on demand. Choose a window with enough headroom for realistic submission delay.

**Retries need a fresh look at the clock.** If a submission fails for an unrelated reason (network blip, sequence number conflict) and your code retries with the _same_ signed envelope, a `maxTime` that was already tight may lapse between attempts. Detect `tx_too_late` and either give up cleanly or rebuild/resign a fresh transaction — don't retry a stale envelope indefinitely.

**Ledger close time has ~5 second granularity.** Stellar ledgers close roughly every 5 seconds; there's no sub-ledger timing precision. Don't design time-locked flows that depend on precision tighter than one ledger interval.

**`minTime` of `0` is easy to forget you're relying on.** If you only ever call `setTimeout()`, `minTime` stays `0`, meaning the transaction is valid immediately once signed — there's no "not before" protection. That's fine for ordinary payments, but if you're building a _scheduled_ disbursement, forgetting to also set `minTime` means anyone holding the signed envelope can submit it right away.

**Time bounds don't replace sequence number protection.** Time bounds prevent a transaction from applying outside its window; they don't by themselves prevent it from applying at all _within_ that window if circumstances change (e.g. you decide to cancel a scheduled payment). If a transaction must be cancellable, you also need a sequence-number strategy — submitting any other transaction from the same source account before the scheduled one invalidates it, since sequence numbers only advance forward.

## Minimal example

A scheduled, self-expiring payment: not submittable for the next hour, and invalid if not submitted within the hour after that.

```typescript
import {
  TransactionBuilder,
  Networks,
  Operation,
  Asset,
} from '@stellar/stellar-sdk';

const now = Math.floor(Date.now() / 1000);
const minTime = now + 3600; // not valid for the next hour
const maxTime = minTime + 3600; // then valid for exactly one hour

const tx = new TransactionBuilder(sourceAccount, {
  fee: '100',
  networkPassphrase: Networks.TESTNET,
})
  .addOperation(
    Operation.payment({
      destination: 'GBOB...',
      asset: Asset.native(),
      amount: '100',
    })
  )
  .setTimebounds(minTime, maxTime)
  .build();

tx.sign(sourceKeypair);

const xdr = tx.toXDR();
// Distribute `xdr` now; submit it (by anyone) only once minTime has passed
```
