# Claimable Balances

A claimable balance lets you send funds to an account that isn't ready to receive them yet — the destination doesn't need a trustline for the asset at send time, and the balance sits on the ledger until someone satisfies the conditions to claim it. This makes them the standard building block for escrow, conditional payouts, airdrops, and time-locked transfers. This guide covers creating a claimable balance, the predicate types that gate claiming, and claiming one.

---

## Creating a claimable balance

Use `Operation.createClaimableBalance` with an asset, an amount, and one or more claimants. Each claimant is a destination account paired with a predicate describing when _that_ claimant is allowed to claim.

```typescript
import {
  Asset,
  Claimant,
  Operation,
  TransactionBuilder,
  Networks,
} from '@stellar/stellar-sdk';

const claimant = new Claimant(
  'GBOB...', // destination account
  Claimant.predicateUnconditional() // anyone holding this claimant slot can claim, any time
);

const transaction = new TransactionBuilder(sourceAccount, {
  fee: '100',
  networkPassphrase: Networks.TESTNET,
})
  .addOperation(
    Operation.createClaimableBalance({
      asset: Asset.native(),
      amount: '100',
      claimants: [claimant],
    })
  )
  .setTimeout(180)
  .build();
```

A single claimable balance can list multiple claimants, each with its own predicate — for example, the intended recipient with an unconditional predicate, and the sender with a predicate that only becomes true after a long timeout, acting as a refund path if the recipient never claims.

## Claim predicates

Predicates are combined from a small set of primitives, all available as static methods on `Claimant`:

| Predicate                                             | Meaning                                                                               |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `Claimant.predicateUnconditional()`                   | Always claimable                                                                      |
| `Claimant.predicateBeforeAbsoluteTime(unixTimestamp)` | Claimable only before a fixed Unix timestamp (as a string, in seconds)                |
| `Claimant.predicateBeforeRelativeTime(seconds)`       | Claimable only within `seconds` of the _ledger close time the balance was created in_ |
| `Claimant.predicateNot(predicate)`                    | Inverts a predicate — combine with the above to express "claimable **after** a time"  |
| `Claimant.predicateAnd(a, b)`                         | Claimable only when both predicates hold                                              |
| `Claimant.predicateOr(a, b)`                          | Claimable when either predicate holds                                                 |

Because there's no `predicateAfter`, "after time X" is expressed as `not(before time X)`:

```typescript
// Claimable only after 2026-08-01T00:00:00Z
const claimableAfterDate = Claimant.predicateNot(
  Claimant.predicateBeforeAbsoluteTime('1785542400')
);
```

A common escrow pattern combines both directions into a claim window:

```typescript
// Claimable only between two dates
const claimWindow = Claimant.predicateAnd(
  Claimant.predicateNot(Claimant.predicateBeforeAbsoluteTime(windowStart)),
  Claimant.predicateBeforeAbsoluteTime(windowEnd)
);

const recipient = new Claimant('GBOB...', claimWindow);
```

> Predicates can nest up to a protocol-defined depth (currently 4 levels). Deeply nested `and`/`or`/`not` trees will be rejected by validators — keep conditions to what you actually need.

## Claiming a balance

Claiming requires the claimable balance's ID, which you get either from the transaction result of the create operation or by querying Horizon's claimable balances endpoint for the claimant:

```typescript
// Look up balances claimable by an account
const { records } = await server.claimableBalances().claimant('GBOB...').call();

const balanceId = records[0].id;
```

```typescript
import { Operation, TransactionBuilder, Networks } from '@stellar/stellar-sdk';

const claimTx = new TransactionBuilder(claimantAccount, {
  fee: '100',
  networkPassphrase: Networks.TESTNET,
})
  .addOperation(Operation.claimClaimableBalance({ balanceId }))
  .setTimeout(180)
  .build();

claimTx.sign(claimantKeypair);
await server.submitTransaction(claimTx);
```

The claim fails with `op_does_not_exist` if the balance was already claimed, and with `op_not_claimable` if the predicate for the submitting claimant does not currently evaluate to true.

## Minimal example

Create a claimable balance the recipient can claim any time, with a 30-day refund path back to the sender if it's never claimed:

```typescript
import {
  Asset,
  Claimant,
  Operation,
  TransactionBuilder,
  Networks,
} from '@stellar/stellar-sdk';

const THIRTY_DAYS = 60 * 60 * 24 * 30;

const recipientClaim = new Claimant(
  recipientPublicKey,
  Claimant.predicateBeforeRelativeTime(String(THIRTY_DAYS))
);

const refundClaim = new Claimant(
  senderPublicKey,
  Claimant.predicateNot(
    Claimant.predicateBeforeRelativeTime(String(THIRTY_DAYS))
  )
);

const tx = new TransactionBuilder(senderAccount, {
  fee: '100',
  networkPassphrase: Networks.TESTNET,
})
  .addOperation(
    Operation.createClaimableBalance({
      asset: Asset.native(),
      amount: '50',
      claimants: [recipientClaim, refundClaim],
    })
  )
  .setTimeout(180)
  .build();

tx.sign(senderKeypair);
await server.submitTransaction(tx);
```

Exactly one of the two claimants can succeed at any given moment — before day 30 only the recipient's predicate is true, and from day 30 onward only the sender's refund predicate is true.
