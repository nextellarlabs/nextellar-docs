# Horizon vs Soroban RPC — Choosing the Right API

Stellar apps typically talk to two different servers: **Horizon**, the classic history and submission API, and **Soroban RPC**, the smart-contract simulation and invocation API. They overlap in a few places (both can submit transactions) but are built for different jobs, and most non-trivial dApps end up using both. This guide compares their features and limits, suggests which one fits common workloads, and covers hybrid usage.

---

## What each API is for

**Horizon** indexes the classic Stellar ledger — accounts, trustlines, offers, payments, effects, and full transaction history — into a queryable REST API, plus server-sent event streams for live updates. It's the API behind account balances, payment lists, the DEX order book, and transaction history in Nextellar's [`useStellarWallet`](/docs/hooks/use-stellar-wallet), [`useStellarBalances`](/docs/hooks/use-stellar-balances), and [`useTransactionHistory`](/docs/hooks/use-transaction-history) hooks.

**Soroban RPC** is the interface to Soroban, Stellar's smart contract platform. It simulates contract invocations (to compute resource fees and return values before submitting), reads contract storage (ledger entries), fetches contract events, and submits transactions that touch contracts. It's the API behind Nextellar's [`useSorobanContract`](/docs/hooks/use-soroban-contract) and [`useSorobanEvents`](/docs/hooks/use-soroban-events) hooks.

## Feature comparison

| Capability                                        | Horizon                                                                                                   | Soroban RPC                                                                                  |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Classic operations (payments, trustlines, offers) | ✅ First-class, fully indexed                                                                             | ⚠️ Can submit them, but no query/history API for them                                        |
| Smart contract invocation                         | ❌ Not supported                                                                                          | ✅ `simulateTransaction`, `sendTransaction`                                                  |
| Contract state reads                              | ❌ Not supported                                                                                          | ✅ `getLedgerEntries`                                                                        |
| Contract events                                   | ❌ Not supported                                                                                          | ✅ `getEvents` (poll-based)                                                                  |
| Historical transaction/operation queries          | ✅ Deep history via indexed database                                                                      | ⚠️ Short retention window (recent ledgers only, unless paired with an archive)               |
| Real-time streaming (SSE)                         | ✅ Payments, transactions, effects, offers                                                                | ❌ No SSE — events are polled via `getEvents`                                                |
| Account/trustline/balance queries                 | ✅ Full account state                                                                                     | ⚠️ Can read raw ledger entries, but not the friendly account model                           |
| Order book / DEX queries                          | ✅ First-class                                                                                            | ❌ Not supported                                                                             |
| Fee model                                         | Flat base fee per operation                                                                               | Resource-based fees computed via simulation (CPU, memory, ledger I/O, plus classic base fee) |
| Rate limits                                       | Per-IP request limits (see [Rate Limiting Horizon Requests](/docs/guides/rate-limiting-horizon-requests)) | Also rate-limited; typically lower quotas on public endpoints than Horizon                   |

## Latency and pagination differences

**Pagination:** Horizon's list endpoints (`payments()`, `transactions()`, `offers()`, etc.) use cursor-based pagination — each response includes `_links.next`/`_links.prev`, and the SDK exposes it as `.cursor()`, `.limit()`, and `.order()`. This makes infinite-scroll history and "load more" UIs straightforward. Soroban RPC has no equivalent list/cursor API: `getEvents` takes a starting ledger and returns a `cursor` you pass to the next call, but it's bounded by a short retention window (recent ledgers only), and reads like `getLedgerEntries` and `simulateTransaction` are single-shot lookups against the latest state with nothing to paginate.

**Latency:** Horizon supports server-sent event streams (`.stream()`) for near-real-time updates as new ledgers close (Stellar ledgers close roughly every 5 seconds). Soroban RPC has no streaming — consumers must poll `getEvents` or `getTransaction`, so effective latency is bounded by your polling interval, not by network push. A typical pattern is polling `getTransaction` every 1–2 seconds until the status leaves `PENDING`, versus subscribing once to a Horizon stream and reacting as events arrive.

## Suggested patterns for common needs

| You need to...                                         | Use                                                                                                                             |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Show an account's XLM/asset balances                   | Horizon (`loadAccount`, or [`useStellarBalances`](/docs/hooks/use-stellar-balances))                                            |
| List or stream a user's payment history                | Horizon (`.payments().forAccount()`, streamed — see [Streaming Payments from Horizon](/docs/guides/streaming-payments-horizon)) |
| Send a classic asset payment                           | Horizon, via `server.submitTransaction()`                                                                                       |
| Call a Soroban contract function                       | Soroban RPC — simulate first, then send (via [`useSorobanContract`](/docs/hooks/use-soroban-contract))                          |
| React to a contract emitting an event                  | Soroban RPC `getEvents`, polled (via [`useSorobanEvents`](/docs/hooks/use-soroban-events))                                      |
| Read a value out of contract storage                   | Soroban RPC `getLedgerEntries`                                                                                                  |
| Show the DEX order book for a trading pair             | Horizon (`.orderbook()`)                                                                                                        |
| Estimate the cost of a contract call before committing | Soroban RPC `simulateTransaction`                                                                                               |
| Look up a transaction from six months ago              | Horizon (full history) — Soroban RPC public endpoints typically retain only recent ledgers                                      |

If a workload isn't in this table, ask: _does it touch a smart contract, or is it a classic-protocol object (account, trustline, offer, classic payment)?_ Classic-protocol reads and writes go to Horizon; anything about contract code, storage, or events goes to Soroban RPC.

## Hybrid usage

Nearly every non-trivial Soroban dApp uses both APIs side by side, because a contract invocation still touches a classic account (the invoker's account, its sequence number, its fee) even though the interesting logic runs in Soroban:

- **Building a Soroban invocation** — load the source account from **Horizon** (`server.loadAccount`) to get its current sequence number, then build and simulate the invocation against **Soroban RPC**, then submit the signed transaction to **Soroban RPC**'s `sendTransaction`.
- **Watching wallet activity while also watching contract activity** — a wallet dashboard commonly streams classic payments from **Horizon** ([Streaming Payments from Horizon](/docs/guides/streaming-payments-horizon)) for the "your balance changed" feed, while separately polling **Soroban RPC** `getEvents` for contract-specific activity (a DEX fill, an NFT transfer) relevant to that same account.
- **Token contracts that wrap classic assets** — Soroban's asset contract interface lets a classic Stellar asset be interacted with through a Soroban contract address. Balance and transfer semantics route through Soroban RPC when going through the contract interface, but the same underlying asset is still visible via Horizon's classic trustline/balance view. Pick the API that matches which interface your code is actually calling through.

A minimal hybrid client:

```typescript
import { Server } from '@stellar/stellar-sdk';
import { Server as SorobanServer } from '@stellar/stellar-sdk/rpc';

const horizon = new Server('https://horizon-testnet.stellar.org');
const soroban = new SorobanServer('https://soroban-testnet.stellar.org');

async function invokeContract(sourcePublicKey: string, operation: any) {
  // Sequence number and fee bookkeeping — Horizon
  const account = await horizon.loadAccount(sourcePublicKey);

  const tx = new TransactionBuilder(account, {
    fee: '100',
    networkPassphrase: Networks.TESTNET,
  })
    .addOperation(operation)
    .setTimeout(30)
    .build();

  // Resource fee simulation and submission — Soroban RPC
  const simulated = await soroban.simulateTransaction(tx);
  const prepared = SorobanRpc.assembleTransaction(tx, simulated).build();

  prepared.sign(sourceKeypair);
  return soroban.sendTransaction(prepared);
}
```
