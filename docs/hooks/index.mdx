# Hooks Overview

Nextellar provides a set of powerful, typed React hooks that simplify working with Stellar accounts, balances, payments, smart contracts, wallets, and DEX edata. These hooks are lightweight, composable, and designed to fit naturally into modern Next.js applications.

---

## Why Hooks in Nextellar?

### Reactive Stellar data

Live updates for accounts, balances, transactions, and contract values.

### Cleaner UI components

Hooks keep UI components free from networking and blockchain logic.

### Built-in loading & error states

Every hook exposes a consistent, predictable return shape.

### Full TypeScript support

Strong types for Stellar responses ensure correctness and better DX.

### Auto-consume provider config

Hooks automatically use `WalletProvider` settings when available.

## **Wallet & Account Hooks**

### [useStellarWallet](/docs/hooks/use-stellar-wallet)

Complete wallet connection and account management. Supports multi-wallet (Freighter, Albedo, Lobstr, xBull, Hana), auto-reconnect, balance fetching, and payment sending.

### [useStellarBalances](/docs/hooks/use-stellar-balances)

Fetch and track XLM and custom asset balances with optional polling. Handles unfunded accounts gracefully.

### [useTrustlines](/docs/hooks/use-trustlines)

## How Nextellar Hooks Work

Nextellar's hooks are designed to stay out of your way and let you build fast. Each hook sits on top of the Stellar SDK and wallet adapters, turning complex blockchain logic into simple, predictable React APIs.

### Auto-Consume Pattern

All hooks automatically consume configuration from `WalletProvider` when available:

```tsx
// Provider sets global config
<WalletProvider horizonUrl="https://horizon.stellar.org">
  <App />
</WalletProvider>;

// Hooks auto-consume the horizonUrl
function MyComponent() {
  const { balances } = useStellarBalances(publicKey);
  // Uses mainnet automatically!
}
```

### Override Per-Component

You can always override the provider config:

```tsx
const { balances } = useStellarBalances(publicKey, {
  horizonUrl: 'https://horizon-testnet.stellar.org',
});
```

### Standalone Usage

Hooks work without a provider too:

```tsx
// No WalletProvider needed
const { balances } = useStellarBalances(publicKey, {
  horizonUrl: 'https://horizon-testnet.stellar.org',
});
```

## Common Patterns

### Loading States

All hooks provide consistent loading and error states:

```tsx
const { data, loading, error, refresh } = useSomeHook();

if (loading) return <Spinner />;
if (error) return <button onClick={refresh}>Retry</button>;
return <DisplayData data={data} />;
```

### XDR Building Pattern

Transaction hooks follow a consistent pattern for wallet integration:

```tsx
// 1. Build unsigned XDR
const xdr = await buildPaymentXDR({ from, to, amount });

// 2. Sign with external wallet (Freighter, etc.)
const signedXdr = await wallet.signTransaction(xdr);

// 3. Submit signed transaction
const result = await submitSignedXDR(signedXdr);
```

## Memoizing Hook Returns

Hook returns are new objects on every render. When you pass those values into child components, into effect dependency arrays, or into other hooks, new references can trigger unnecessary work. Memoization keeps those references stable without changing the data the hook returns.

### When memoization matters

Memoization is worth it when:

- A hook returns an object or array (for example, `useStellarBalances` returns a `balances` array) and you pass it to a memoized child or a context provider.
- You derive data from a hook return and use it inside `useEffect`, `useMemo`, or `useCallback`.
- You store a hook return in a dependency array and the reference changes on every render even when the underlying data is identical.

Memoization is not needed when the hook returns primitives (`string`, `number`, `boolean`) or when the value is only read inside the same component. Prefer memoizing at the consumer site instead of wrapping every hook call.

### Example

The following component memoizes the balance list and the derived total so children and effects only re-run when the data actually changes:

```tsx
import { useMemo } from 'react';
import { useStellarBalances } from '@nextellar/hooks';

export function BalanceSummary({ publicKey }: { publicKey: string }) {
  const { balances, loading, error } = useStellarBalances(publicKey);

  // Stable reference for the derived total.
  const total = useMemo(
    () => balances.reduce((sum, balance) => sum + Number(balance.balance), 0),
    [balances],
  );

  // Stable reference for the row data passed to children.
  const rows = useMemo(
    () => balances.map((balance) => ({
      asset: balance.asset_type === 'native' ? 'XLM' : balance.asset_code,
      amount: balance.balance,
    })),
    [balances],
  );

  if (loading) return <p>Loading balances…</p>;
  if (error) return <p>Could not load balances.</p>;

  return (
    <section>
      <p>Total: {total}</p>
      <ul>
        {rows.map((row) => (
          <li key={row.asset}>
            {row.asset}: {row.amount}
          </li>
        ))}
      </ul>
    </section>
  );
}
```

### Guardrails

- Memoize on the values the hook returns, not on the hook call itself. If a dependency is a new object on every render, the memo will recompute anyway.
- Keep dependency arrays minimal and exact. Include the hook return values you actually read and avoid spreading the entire return object into dependencies.
- Do not memoize data that changes on every poll. If `useStellarBalances` is polling, the balances array will change when data changes, which is the intended behavior.
- Prefer deriving values with `useMemo` instead of storing them in state. State adds an extra render and can go stale.
- When passing hook returns through context, memoize the context value so consumers do not re-render on every provider render.
- Remember that `React.memo` and `useMemo` are optimizations, not correctness guarantees. Verify behavior without them first, then add memoization where profiling shows it helps.
