# Search Index Pipeline Documentation

## Overview

The Nextellar docs site features a **client-side search index pipeline** that automatically builds, validates, and deploys a searchable index of all documentation content. This enables fast, offline-capable search functionality without requiring a backend search service.

## Architecture

### Components

1. **Build Script** (`scripts/build-search-index.cjs`)
   - Crawls the Contentlayer2-generated docs
   - Extracts title, headings, and body text from each document
   - Strips markdown/MDX syntax for clean content
   - Generates a structured JSON index artifact
   - Output: `public/search-index.json`

2. **Validation Script** (`scripts/validate-search-index.cjs`)
   - Validates the generated index before it's used
   - Ensures file size is reasonable (>1 KB)
   - Verifies JSON schema and structure
   - Checks document count meets minimum threshold (10+)
   - Validates all required document fields exist
   - Cross-checks index paths against source docs
   - Validates content is not empty/corrupted
   - **Fails the CI pipeline if any check fails**

3. **Unit Tests** (`scripts/validate-search-index.test.ts`)
   - Comprehensive Vitest suite for validation logic
   - Tests file validation, schema, document count, structure, paths, and content
   - Includes integration tests for multi-version indexes
   - Uses mock data to test success and failure scenarios

4. **CI/CD Workflow** (`.github/workflows/search-index-ci.yml`)
   - Automatically runs on PRs and pushes to main/develop
   - Triggers when docs or pipeline-related files change
   - Builds content → generates index → validates → runs tests
   - Uploads index artifact for inspection
   - Comments on PRs with results and statistics

5. **Search UI Component** (`src/components/search-dialog.tsx`)
   - Already integrated with Next.js app
   - Accepts searchData prop (the index documents)
   - Provides Cmd+K keyboard shortcut for search
   - Real-time filtering and highlighting of results

## How It Works

### Building the Index

```bash
npm run build:search-index
```

**Process:**
1. Reads `.contentlayer/generated/index.js` (generated by Contentlayer2 build)
2. Iterates through all documents (including versioned docs)
3. For each document:
   - Extracts title and description from frontmatter
   - Parses markdown to extract heading hierarchy
   - Strips markdown syntax from body content
   - Determines document version (latest or specific version like v1.0.0)
   - Creates searchable entry with cleaned content
4. Writes `public/search-index.json` with:
   - Version metadata
   - Generation timestamp
   - Document count
   - Full documents array

**Output Structure:**
```json
{
  "version": "1.0.0",
  "generatedAt": "2026-09-24T00:37:35.354Z",
  "documentCount": 15,
  "documents": [
    {
      "id": "getting-started/intro",
      "title": "Getting Started",
      "description": "Introduction to Nextellar",
      "headings": ["Installation", "Configuration"],
      "body": "Install Nextellar CLI globally...",
      "path": "/docs/getting-started/intro",
      "version": "latest"
    },
    // ... more documents
  ]
}
```

### Validating the Index

```bash
npm run validate:search-index
```

**Validation Checks:**

| Check | Requirement | Reason |
|-------|-------------|--------|
| **File Exists** | Index file must exist | Catches missing/broken build |
| **File Size** | ≥ 1 KB | Catches silently broken crawl |
| **JSON Valid** | Must parse as valid JSON | Catches corruption |
| **Schema** | Has version, generatedAt, documentCount, documents | Ensures structure |
| **Document Count** | ≥ 10 documents | Catches incomplete crawl |
| **Required Fields** | Each doc has id, title, path, version | Ensures completeness |
| **Path Format** | All paths start with `/docs/` | Ensures URL validity |
| **Paths Exist** | Paths match source documents | Catches stale index |
| **Content** | <50% empty titles/bodies | Catches corruption |

**Failure Behavior:**
- Any validation failure exits with code 1
- CI pipeline fails immediately
- PR comments show specific failure reason
- Index is not deployed

### Running Tests

```bash
npm run test:validation
```

Tests verify validation logic works correctly by:
- Creating valid test indexes and confirming they pass
- Creating deliberately broken indexes (missing fields, too few docs, invalid paths) and confirming they fail
- Testing edge cases (empty content, malformed JSON, missing metadata)
- Validating multi-version indexes are handled correctly

## Integration with CI/CD

### GitHub Actions Workflow

The `.github/workflows/search-index-ci.yml` workflow:

**Triggers:**
- On push to `main` or `develop` branches
- On PRs to `main` or `develop` branches
- Only when docs or pipeline files change

**Steps:**
1. Checkout code
2. Setup Node.js (v18.x)
3. Setup pnpm with caching
4. Install dependencies
5. Build content: `pnpm build:content`
6. Build search index: `pnpm build:search-index`
7. Validate search index: `pnpm validate:search-index`
8. Run tests: `pnpm test:validation`
9. Upload index artifact (30-day retention)
10. Comment on PR with results

**PR Comments:**

✅ **Success comment shows:**
- Document count indexed
- File size
- Generation timestamp
- Index version
- All passed checks

❌ **Failure comment shows:**
- Which step failed
- Guidance on common fixes
- Link to workflow logs

## Versioning Support

The index supports versioned documentation:

**Version Detection:**
- **Latest/Current:** Docs in `docs/` folder → version = "latest"
- **Versioned:** Docs in `docs/versions/v1.0.0/` → version = "1.0.0"

**Index Output:**
Each document includes:
- `version` field indicating which version it belongs to
- `path` field with full URL including version (e.g., `/docs/v1.0.0/guide`)

**Search Behavior:**
The SearchDialog component searches across all versions. Users can see which version a result is from in the index, enabling future filtering if needed.

## Performance Characteristics

- **Build Time:** ~1-2 seconds (depends on doc count)
- **Index Size:** ~5-10 KB (for 15 docs; scales linearly)
- **Validation Time:** <500ms
- **Search Performance:** Client-side; instant results on modern browsers

## Troubleshooting

### Index Build Fails

**Issue:** `Contentlayer index not found`
- **Cause:** Contentlayer hasn't run
- **Fix:** Run `npm run build:content` first

**Issue:** `Could not parse allDocs from contentlayer index`
- **Cause:** Contentlayer output format changed
- **Fix:** Check `.contentlayer/generated/index.js` structure

### Validation Fails

**Issue:** `Too few documents indexed`
- **Cause:** Docs folder missing or no .mdx files
- **Fix:** Ensure docs exist in `docs/` folder with proper structure

**Issue:** `Missing required top-level field`
- **Cause:** Index file corrupted or incomplete
- **Fix:** Delete `public/search-index.json` and rebuild

**Issue:** `Index references non-existent paths`
- **Cause:** Index built with old/deleted docs
- **Fix:** Ensure `docs/` folder is current and rebuild

### Search Not Working

**Issue:** SearchDialog shows no results
- **Cause:** Index not loaded in browser
- **Fix:** Verify `public/search-index.json` exists and is valid

**Issue:** Results show wrong content
- **Cause:** Index out of date
- **Fix:** Run `npm run build:search-index` to regenerate

## Best Practices

1. **Always rebuild index after adding docs:** The index won't reflect new content until `npm run build:search-index` runs.

2. **Ensure all docs have titles:** The validation requires non-empty titles to catch formatting issues.

3. **Review CI failures:** If the workflow fails, check the logs for the specific validation error and fix it before merging.

4. **Use Cmd+K to test search:** Press Cmd+K (Mac) or Ctrl+K (Windows/Linux) to open search and verify results match your new docs.

5. **Commit the index:** `public/search-index.json` should be committed to version control for production builds.

## FAQ

**Q: Do I need to manually run the build script?**
A: No. It runs automatically in CI on every PR/push. For local testing, run `npm run build:search-index`.

**Q: Where does the index get stored?**
A: `public/search-index.json` - this is served as a static asset and downloaded by the browser.

**Q: Is the search index updated in production?**
A: Yes. Every merge to main triggers the workflow, regenerates the index, and uploads it. The next deployment uses the new index.

**Q: Can I search across multiple versions?**
A: Yes. The index includes all versions (latest + versioned). Results show which version each doc belongs to.

**Q: What happens if validation fails in CI?**
A: The PR check fails, blocking merge. The failure reason is commented on the PR. Fix the issue and push again.

**Q: How do I test validation locally?**
A: Run `npm run test:validation` to execute the full test suite with mock data.
