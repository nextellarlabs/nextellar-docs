# Revoking Trust for an Asset

Asset issuers on Stellar can control whether holders may keep or receive an issued asset by changing trustline authorization flags. This guide covers the `allow_trust` / `set_trust_line_flags` path, product and legal implications, and a small example.

## Before You Start

Revoking trustline access affects real users and balances. Before changing trustline authorization:

- Confirm the legal basis for restricting an asset holder in your jurisdiction and product terms.
- Communicate the action to affected users before or at the time of enforcement when possible.
- Review the asset's issuer flags. Trustline authorization controls only work when the issuing account is configured with the relevant authorization flags.
- Test on testnet before applying changes to mainnet accounts.

## Authorization Model

Stellar trustline authorization is controlled by the issuing account's flags and per-trustline operations:

| Flag / operation | Purpose | Typical use |
| --- | --- | --- |
| `AUTH_REQUIRED` (`AUTH_REQUIRED_FLAG`) | New trustlines must be authorized by issuer | KYC-gated assets |
| `AUTH_REVOCABLE` (`AUTH_REVOCABLE_FLAG`) | Issuer can revoke existing trustline authorization | Compliance or enforcement controls |
| `AUTH_CLAWBACK_ENABLED` (`AUTH_CLAWBACK_ENABLED_FLAG`) | Issuer can claw back issued balances | Regulated asset recovery; separate from revocation |
| `SetTrustLineFlags` | Set/clear specific trustline flags for an asset holder | Preferred granular control |
| `AllowTrust` (deprecated path) | Legacy operation to authorize/deauthorize trustline | Older integrations; prefer `SetTrustLineFlags` |

> [!NOTE]
> `AllowTrust` is a legacy operation. For new implementations, prefer `SetTrustLineFlags`, which supports explicit flag changes including authorized, authorized-to-maintain-liabilities, and clawback-enabled flags.

## Revoke or Freeze Access with `SetTrustLineFlags`

To revoke a holder's ability to transact an issued asset, the issuer clears the trustline's authorized flags. A common pattern is:

- **Fully authorized**: holder can receive, hold, send, and trade.
- **Authorized to maintain liabilities**: holder can maintain existing offers but cannot receive new funds or create new offers in ways restricted by authorization. Use this as a "freeze"/limited state when appropriate.
- **Not authorized**: holder cannot receive or send the asset as authorized; use for full revocation.

### Small Example (TypeScript)

This example shows an issuer revoking full authorization and allowing only maintenance of liabilities using `SetTrustLineFlags`. It uses `@stellar/stellar-sdk` and should run in a secure server environment because it requires the issuer secret key.

```ts
import {
  Asset,
  Horizon,
  Keypair,
  Networks,
  Operation,
  TransactionBuilder,
} from '@stellar/stellar-sdk';

const horizonUrl = 'https://horizon-testnet.stellar.org';
const server = new Horizon.Server(horizonUrl);

async function revokeTrustline({
  issuerSecret,
  holderAccountId,
  assetCode,
}: {
  issuerSecret: string;
  holderAccountId: string;
  assetCode: string;
}) {
  const issuer = Keypair.fromSecret(issuerSecret);
  const asset = new Asset(assetCode, issuer.publicKey());
  const issuerAccount = await server.loadAccount(issuer.publicKey());

  const tx = new TransactionBuilder(issuerAccount, {
    fee: '100',
    networkPassphrase: Networks.TESTNET,
  })
    .addOperation(
      Operation.setTrustLineFlags({
        trustor: holderAccountId,
        asset,
        flags: {
          authorized: false,
          authorizedToMaintainLiabilities: true,
        },
      }),
    )
    .setTimeout(30)
    .build();

  tx.sign(issuer);
  return server.submitTransaction(tx);
}
```

To fully deauthorize the trustline, set both `authorized` and `authorizedToMaintainLiabilities` to `false`.

## Legacy `AllowTrust` Path

Older systems may still use `AllowTrust`. It takes the trustor account, asset code, and authorize value. The operation is limited compared with `SetTrustLineFlags` and is not recommended for new implementations.

```ts
Operation.allowTrust({
  trustor: holderAccountId,
  assetCode: 'USD',
  authorize: 0, // 0: not authorized, 1: authorized, 2: authorized to maintain liabilities
});
```

## Legal and Product Implications

Trustline revocation is a technical control, not a complete compliance or legal process. Consider:

- **Legal authority**: Ensure your terms of service, token program documentation, and applicable law permit freezing or revoking access. Regulated assets may require specific disclosures and procedures.
- **Customer impact**: Revocation can prevent users from receiving or moving assets. Provide clear user communication, support paths, and appeal/escalation processes where required.
- **Liabilities and open offers**: If a user has open DEX offers or liabilities, full revocation may be operationally disruptive. `authorizedToMaintainLiabilities` can reduce disruption while preventing new activity.
- **Auditability**: Log who initiated the action, when, why, and the transaction hash. Keep records according to your compliance obligations.
- **Clawback is different**: Revoking authorization does not remove existing balances. Clawback, where enabled and legally permitted, is a separate operation with its own legal and user-impact considerations.
- **Mainnet finality**: Transactions are final once confirmed. Use careful review, role-based access, and testnet rehearsals for operational procedures.

## Verify the Change

After submitting the transaction:

1. Query Horizon for the holder's account and inspect the trustline flags for the asset.
2. Confirm the transaction succeeded and record the hash.
3. Validate expected behavior in your product UI and any trading/routing logic.
4. Notify affected users according to your policy.

```bash
curl "https://horizon-testnet.stellar.org/accounts/<HOLDER_ACCOUNT_ID>"
```

Look for the asset's trustline entry and check `is_authorized` / `is_authorized_to_maintain_liabilities` fields.
